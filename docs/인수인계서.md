# 읽어 주십시오

## 1. 서비스 소개

TRAVENDER 본 사이트에 붙는 **홋카이도 골프 버스 패키지 예약 서비스**입니다. 모바일 웹이 기본이고, PC에서는 넓은 배치로 보입니다. 화면 문구는 한국어와 일본어입니다.

### 이 문서에서 쓰는 말

| 말 | 뜻 |
|---|---|
| 예약자 | 예약한 본 사이트 회원 (대표자). 함께 가는 사람은 동반자 |
| 예약 취소 | 예약자가 고객센터에 요청해 **예약 하나**를 취소. 환불은 본 사이트가 처리 |
| 운행 취소 | 최소 인원이 모이지 않아 **출발편 자체**를 취소. 그 출발편의 확정 예약이 모두 취소되고, 골프 서버가 전액 환불을 요청 |
| 주문 취소 | 본 사이트의 **결제 주문**이 취소됨 (결제 전). 예약은 미결제가 되고 자리가 풀림 |
| 출발편 | 패키지의 출발일 하나 (예: 패키지 A의 5월 10일 출발) |

### 예약자가 하는 일

```
패키지 고르기 (목록·검색·비교)
 → 출발일 고르기 (남은 자리 표시)
 → 호텔·객실 고르기 (숙박 패키지만)
 → 승하차 장소 고르기: 첫날 타는 곳, 마지막 날 내리는 곳 (삿포로 시내 5km 안)
 → 예약 내용과 금액 확인
 → 예약자·동반자 정보 입력          ← 여기서 예약번호가 나오고 자리를 잡아 둡니다
 → 본 사이트 결제창에서 카드 결제
 → 예약 완료
```

- 중간 날에는 묵는 호텔 앞에서 탑니다. 예약자가 고르지 않습니다.
- 당일치기는 같은 날 타는 곳과 내리는 곳을 고릅니다.
- 예약자 화면에는 예약 취소 버튼이 없습니다. 예약 취소는 고객센터로만 받습니다.

### 예약한 뒤에 자동으로 일어나는 일

```
출발 7일 전 오전 9시: 출발 판정
 ├ 최소 인원이 모임   → 출발 확정 → 예약자에게 출발 확정 메일
 └ 최소 인원이 안 모임 → 운행 취소 → 본 사이트에 전액 환불 요청 → 운행 취소 메일

운영사가 승차 순서·승차 시간을 등록 → 예약자의 예약 상세 화면에 표시

여행이 끝난 다음 날 오전 9시: '여행 완료'로 바뀜
```

### 지금 상태

| 기능 | 상태 |
|---|---|
| 예약 흐름 전체 (패키지 → 결제 → 완료) | ✅ 완성 |
| 내 예약 목록·상세, 동반자 이름 수정 | ✅ 완성 |
| 본 사이트 로그인·주문·결제 결과 확인·환불 | ✅ 완성, 본 사이트 테스트 서버에서 확인함 (11/11) |

| 상품 일괄 가져오기 | ❌ 자리만 있음 → 15장 |

## 2. 우리가 이렇게 만든 이유

코드를 고치실 때 이 원칙이 깨지지 않도록 해 주십시오. 대부분 테스트로 지키고 있습니다 (3장).

### ① 카드 정보는 다루지 않습니다
결제는 본 사이트 결제창이 합니다. 골프 서비스는 "얼마짜리 주문"을 만들고 결과만 물어봅니다. 그래서 카드 정보가 골프 서버를 지나가지 않습니다.

### ② 결제 성공은 직접 확인합니다
결제 뒤 돌아온 주소만 보고 성공으로 처리하지 않습니다. 주소는 누구나 흉내 낼 수 있기 때문입니다. 골프 서버가 본 사이트에 "이 주문 결제됐나요?"를 직접 묻고, 그 답으로만 예약을 확정합니다. 예약자가 결과 화면에 돌아오지 않아도 10분마다 같은 확인을 합니다.

### ③ 결제하는 동안 자리를 빼앗기지 않게 합니다
결제창으로 가기 **전에** 예약을 '결제 대기'로 만들고 자리를 잡아 둡니다. 결제를 마쳤는데 그사이 자리가 다 차는 일을 막기 위해서입니다.
- 결제하기를 누르기 전에는 10분만 잡아 둡니다.
- 결제창에 들어간 뒤에는 결과가 나올 때까지 잡아 둡니다.

### ④ 정원을 넘겨 팔지 않습니다
여러 예약자가 동시에 마지막 자리를 잡아도 한 명만 성공합니다. 출발편을 잠그고 남은 자리를 다시 세는 방식입니다. DB 격리 수준도 이 때문에 READ COMMITTED로 바꿨습니다.

### ⑤ 같은 일이 여러 번 일어나도 결과는 한 번입니다
결제하기를 두 번 누르거나, 결과 화면과 자동 확인이 동시에 결제를 반영하거나, 작업이 중간에 멈췄다가 다시 돌아도 아래가 지켜집니다.
- 주문은 하나만 만들어집니다.
- 확정 인원은 한 번만 늘어납니다.
- 환불은 한 번만 요청합니다.
- 메일은 한 번만 보냅니다.

### ⑥ 늦게 들어온 결제는 확정하지 않고 돌려줍니다
'미결제'로 끝나 자리가 풀린 예약에 나중에 결제가 들어오면, 그 자리는 이미 다른 예약자에게 갔을 수 있습니다. 그래서 확정하지 않고 자동으로 전액 환불하고, 운영자에게 알립니다.

### ⑦ 금액은 서버가 계산합니다
화면에 보이는 금액은 참고용입니다. 본 사이트에 보내는 금액은 항상 서버가 다시 계산한 값입니다. 화면 값을 조작해도 금액이 바뀌지 않습니다.

### ⑧ 실패해도 멈추지 않고, 사람에게 알립니다
- 메일 발송이 실패해도 예약은 그대로 둡니다. 실패한 메일은 매시 30분에 다시 보냅니다.
- 환불이 실패하면 매시 30분에 다시 요청하고, 운영자에게 알립니다.
- 출발 판정이 실패하면 3번까지 다시 하고, 그래도 안 되면 운영자에게 알립니다.

### ⑨ 운영 서버에서는 위험한 설정을 거부합니다
가짜 결제 모드, 날짜 고정, 예시 키(`change-me`)로는 운영 서버가 아예 켜지지 않습니다. 실수로 '결제 없이 예약되는 서버'가 열리는 것을 막기 위해서입니다.

### ⑩ 운영은 단순하게
- 승하차 범위는 모든 패키지가 같은 '삿포로 중심 5km' 하나입니다. 패키지마다 다른 규칙을 두면 예약자 안내와 운영이 복잡해지기 때문입니다.
- 예약자에게 희망 승차 시간을 받지 않습니다. 운영이 동선을 보고 정하고, 예약자는 요청 사항만 남깁니다.

### ⑪ 개인정보는 필요한 곳에만
작업 기록과 서버 로그에는 개인정보(이름·연락처)를 남기지 않습니다. 회원 정보는 본 사이트에 있고, 골프 DB에는 본 사이트 회원 번호만 저장합니다.

### ⑫ 시간과 날짜 기준
시각은 UTC로 저장하고, 출발일 같은 날짜는 일본 달력 날짜로 저장합니다. 서버가 어느 나라에 있어도 결과가 같습니다.

### 3-2. 본 사이트 테스트 서버로 직접 확인 (2026-11-11)

**가정**
- 개발 PC(localhost)에서 골프 서버를 켜고, 실제 본 사이트 **테스트 서버**에 연결했습니다.
- 개발 PC는 본 사이트와 도메인이 달라서, 로그인 쿠키를 직접 옮겨 넣고 결제 뒤 주소를 직접 바꿔서 확인했습니다 (11장 '개발 PC에서 테스트 서버로 시험하기').
- 테스트 회원과 테스트 카드를 썼습니다. 실제 돈은 움직이지 않았습니다.

**결과**

```
로그인 확인 ✅ → 주문 만들기 ✅ → 테스트 카드 결제 ✅ → 결제 결과 확인·예약 확정 ✅ → 환불 ✅ → 로그아웃 ✅
```

**이때 찾아서 고친 것**

| 문제 | 원인 | 고친 것 |
|---|---|---|
| 결제하기를 누르면 "결제가 완료되지 않았습니다" | 회원 번호를 글자(`"3"`)로 보냄. 본 사이트는 숫자를 기대함 | 숫자로 보냄 |
| 로그아웃하면 "페이지에 연결할 수 없음" | 본 사이트 로그아웃은 POST만 받음 | 폼 전송(POST)으로 로그아웃 |
| 오류 원인을 알 수 없음 | 서버 로그에 오류 코드만 남음 | 본 사이트가 보낸 설명도 로그에 남김 |

### 3-3. 확인하지 못한 것

| 항목 | 이유 |
|---|---|
| 본 사이트와 같은 도메인에 올린 상태의 로그인·결제 뒤 돌아오기·로그아웃 | 아직 올릴 주소가 정해지지 않음 |
| 본 사이트가 실제로 예약 취소 결과를 보내는 흐름 | 본 사이트 쪽 기능이 아직 없음 (받는 쪽은 자동 테스트로 확인) |
| 같은 예약으로 주문을 다시 만들 때의 본 사이트 응답, 환불 응답 모양 | 본 사이트 사양서 원본을 받지 못함 (가짜 본 사이트로는 확인) |
| 실제 메일 도메인으로 발송 | 보내는 주소가 아직 테스트용 |
| 많은 예약자가 한꺼번에 들어오는 경우 (부하) | 시험하지 않음 |
| 운영 DB에 실제 상품을 넣은 상태의 화면 | 상세 화면이 아직 시연용 데이터 (18장 1번) |

## 4. ⚠ 주의점 

### A. 운영을 시작하기 전에 꼭 해야 할 것

| # | 할 일 | 하지 않으면 |
|---|---|---|
| A1 | 패키지 상세 화면이 서버 데이터를 읽게 바꾸기 (18장 1번) | DB에 상품을 넣어도 상세·호텔 선택 화면에 시연용 내용이 나옴 |
| A2 | 본 사이트에서 예약 취소 결과를 골프 서버로 보내게 하기 (15장 '예약 취소 알림') | 예약을 취소해도 자리가 그대로 차 있고, 예약을 취소한 예약자가 출발 인원에 들어가고, 출발 확정 메일까지 감 |
| A3 | 골프 화면과 서버를 **본 사이트와 같은 도메인**에 올리기 (8장) | 로그인이 이어지지 않고, 결제 뒤 골프 화면으로 돌아오지 않음 |
| A4 | Google 지도 키에 사용 도메인 제한 걸기 (Google Cloud 콘솔) | 키가 화면에 그대로 보여 남이 쓰고 요금이 나올 수 있음 |
| A5 | 메일 보내는 주소를 실제 주소로 바꾸고 도메인 인증(SPF·DKIM) | 테스트 주소라 예약자에게 메일이 안 가거나 스팸 처리 |
| A6 | 최소 출발 인원을 운영 값으로 (지금 테스트용 15명, 20장) | 판정 기준이 운영 의도와 다름 |
| A7 | 고객센터 번호·서비스 이름·약관 링크를 실제 값으로 (19장) | 예약자에게 임시 번호(`00-0000-000`)가 보임 |
| A8 | 운영 DB에 시연용 데이터(`seed`)를 넣지 않기 | 시연용 패키지 7개가 판매됨 |

### B. 운영 서버 설정

| # | 주의 |
|---|---|
| B1 | `APP_ENV=production`, `PAYMENT_BACKEND=partner`, `FIXED_TODAY`는 비움. 어기면 서버가 켜지지 않습니다 |
| B2 | 운영 키(`ADMIN_KEY`)는 쓰지 않으면 **비워 두십시오**. 비어 있으면 운영 기능은 모든 요청을 거부합니다. 예시값 `change-me`면 서버가 켜지지 않습니다 |
| B3 | 본 사이트 키(`SITE_KEY`)는 긴 무작위 값으로 정해 본 사이트와만 나눠 가지십시오 |
| B4 | `JOBS_ENABLED=1`이어야 결제 확인·출발 판정·환불 재시도가 자동으로 돕니다. 서버를 여러 대 띄워도 DB 잠금으로 한 곳에서만 돌지만, 관리하기 쉽게 한 대에만 켜는 것을 권합니다 |
| B5 | 키와 비밀번호(`.env`)는 git에 올리지 마십시오. `.env`는 `.gitignore`에 들어 있습니다 |
| B6 | 저장소를 공개하면 **지난 커밋 기록도 공개됩니다**. 지운 파일도 기록에서는 볼 수 있으니, 공개 전에 기록에 키나 내부 자료가 없는지 확인해 주십시오 |

### C. 운영하면서

| # | 주의 |
|---|---|
| C1 | 운영자 알림 메일(`OPS_EMAIL`)을 꼭 받는 주소로. 환불 실패·판정 실패·늦은 결제는 사람이 확인해야 합니다 (14장) |
| C2 | 판매를 멈출 때 패키지를 지우지 말고 `published = 0`. 예약이 있는 출발편과 연결되어 있습니다 |
| C3 | 승차 시간은 출발 3일 전까지 등록. 등록한 시간은 출발 확정된 예약에만 예약자에게 보입니다 |
| C4 | 결제 대기가 60분 넘게 이어지면 알림이 옵니다. 그동안 자리는 계속 잡혀 있습니다 |

### D. 코드를 고칠 때

| # | 주의 |
|---|---|
| D1 | 코드를 새로 받으면 `alembic upgrade head`. DB 구조가 옛 버전이면 서버 오류가 납니다 |
| D2 | DB 구조를 바꿀 때는 새 Alembic 버전을 추가하십시오. 처음 구조 파일(`schema_0001.sql`)은 고치지 않습니다 |
| D3 | 업무 기준 값은 **서버와 화면 두 곳**에 있습니다 (`apps/api/app/settings.py`, `packages/shared/src/settings.ts`). 같이 고치십시오 |
| D4 | 테스트는 `golf_test` DB를 지우고 다시 만듭니다. 운영 DB 주소로 돌리지 마십시오 |
| D5 | 본 사이트 연동 중 사양서로 확인하지 못한 부분은 `apps/api/app/adapters/partner.py` 맨 위 '가정' 목록에 모여 있습니다. 사양서와 다르면 그곳만 고치면 됩니다 |
| D6 | 2장의 원칙(특히 ②④⑤⑥⑦)을 깨는 변경은 테스트가 실패합니다. 테스트를 지우지 말고 원인을 확인해 주십시오 |

## 7. 설정 (.env)

저장소 루트의 `.env`입니다. 모든 이름과 설명은 `.env.example`에 있습니다.

| 이름 | 뜻 | 운영 서버 값 |
|---|---|---|
| `APP_ENV` | `test` 또는 `production` | `production` |
| `DATABASE_URL` | MySQL 접속 주소 | 운영 DB |
| `PAYMENT_BACKEND` | `fake` 가짜 본 사이트 / `partner` 실제 본 사이트 | `partner` |
| `PARTNER_API_BASE`, `PARTNER_API_KEY` | 본 사이트 Partner API 주소와 키 | 본 사이트에서 받은 값 |
| `PARTNER_TIMEOUT` | 본 사이트 응답 대기 (초) | 10 |
| `LOGIN_URL`, `LOGOUT_URL` | 본 사이트 로그인·로그아웃 주소 | `/login`, `/logout` |
| `PAYMENT_RETURN_URL` | 결제 뒤 돌아올 골프 결과 화면. `{no}`에 예약번호가 자동으로 들어감 (**그대로 두십시오**) | `https://<도메인>/<골프 경로>/#/golf/payment/return?no={no}` |
| `SITE_KEY` | 본 사이트가 예약 취소 결과를 보낼 때의 키 | 긴 무작위 값 |
| `ADMIN_KEY` | 운영 기능 키 | 비움 (4장 B2) |
| `JOBS_ENABLED` | 정기 작업 | `1` |
| `FIXED_TODAY` | 오늘 날짜 고정 (테스트용) | 비움 |
| `OPS_EMAIL` | 운영자 알림 받을 메일 | 운영 담당 주소 |
| `MAIL_BACKEND` | `smtp` 실제 발송 / `log` 기록만 | `smtp` |
| `MAIL_FROM`, `MAIL_FROM_NAME`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY`, `SMTP_USER`, `SMTP_PASSWORD` | 메일 발송 | 실제 메일 서버 |
| `SUPPORT_TEL`, `SUPPORT_EMAIL` | 고객센터 연락처 (메일·화면) | 실제 값 |

화면을 빌드할 때 쓰는 값 (`apps/web/.env.local` 또는 빌드할 때 환경 변수):

| 이름 | 뜻 | 운영 빌드 |
|---|---|---|
| `VITE_USE_API` | 서버 API 사용 | `1` |
| `VITE_GOOGLE_MAPS_API_KEY` | Google 지도 키 | 운영 키 (4장 A4) |
| `VITE_SITE_URL` | 본 사이트 주소 (헤더 링크) | 본 사이트 주소 |

## 10. 예약 상태와 흐름

### 예약 상태

| 값 | 화면 표시 | 자리 |
|---|---|---|
| `PENDING_PAYMENT` | 결제 대기 | 잡혀 있음 |
| `UNPAID` | 미결제 (실패·만료·그만둠) | 풀림 |
| `CONFIRMED` | 예약 확정 | 확정 인원에 들어감 |
| `USER_CANCEL` | 예약 취소 (예약자 요청) | 풀림 |
| `OP_CANCEL` | 운행 취소 (최소 인원 미달) | — |
| `DONE` | 여행 완료 | — |

```
정보 입력 완료 → 결제 대기
 ├ 10분 안에 결제하기를 안 누름        → 미결제
 ├ 결제하기 → 본 사이트 주문 → 결제창
 │   ├ 결제됨                         → 예약 확정
 │   ├ 실패·만료·본 사이트에서 주문 취소 → 미결제
 │   └ 카드 인증 중                    → 결제 대기 그대로 (자리 유지)
 ├ 결제 화면에서 뒤로 가기              → 미결제
 └ 같은 회원이 새 예약을 시작           → 결제창만 열린 이전 주문은 미결제로 (카드 인증 중이면 그대로)

미결제 뒤에 결제가 들어옴 → 확정하지 않고 자동 전액 환불 + 운영자 알림

예약 확정 → 출발 판정 → 출발 확정 → 여행 완료
                     └→ 운행 취소 → 전액 환불 요청 (실패하면 매시 30분 다시)
예약 확정 → 고객센터에서 예약 취소 → 예약 취소
```

### 출발편 상태

| 값 | 뜻 |
|---|---|
| `OPEN` | 모집 중 |
| `GO` | 출발 확정 |
| `CANCEL` | 운행 취소 |
| `DONE` | 여행 완료 |

### 누가 예약을 취소했나 (`booking.cancel_by`)

| 값 | 뜻 | 환불 |
|---|---|---|

| `SYSTEM` | 자동 처리 | |

## 11. 본 사이트 연동

본 사이트 API는 **골프 서버에서만** 부릅니다. 모든 요청에 헤더 `X-Api-Key: <PARTNER_API_KEY>`를 붙입니다.

### 골프 서버 → 본 사이트

| 하는 일 | 요청 | 언제 |
|---|---|---|
| 로그인 확인 | `GET /api/partner/session`, 헤더 `X-User-Session: <user_session 쿠키 값>` | 로그인이 필요한 요청마다 (요청당 한 번). 404 `no_session`이면 본 사이트 로그인으로 안내 |
| 주문 만들기 | `POST /api/partner/orders` `{reference, amount, title{ja,ko}, user_id(숫자), return_url, departure_date, heads}` | 결제하기를 누를 때 |
| 주문 조회 | `GET /api/partner/orders/{order_id}` | 결과 화면, 10분마다 결제 확인 |
| 환불 | `POST /api/partner/orders/{order_id}/cancel` `{reason}` | 운행 취소·늦은 결제(`operator_cancel`), 운영 기능 예약 취소(`customer_cancel`) |

### 테스트 서버에서 알게 된 본 사이트 규칙 (코드에 반영됨)

- 주문의 `user_id`는 **숫자**여야 합니다. 글자면 400 `body is not valid JSON`.
- `return_url`은 **본 사이트 도메인의 https 주소**만 받습니다.
- 로그아웃(`/logout`)은 **POST만** 받습니다.
- 오류 응답은 `{"error": "<코드>", "message": "<설명>"}`입니다. 골프 서버 로그에 `partner error <상태> <코드> <응답>`으로 남습니다.

### 본 사이트 → 골프 서버

예약 취소 결과를 받는 주소가 있습니다. 15장 '예약 취소 알림'을 보십시오.

### 개발 PC에서 테스트 서버로 시험하기

개발 PC(localhost)는 본 사이트와 도메인이 달라 두 가지를 직접 해야 합니다.

```
1. .env
   PAYMENT_BACKEND=partner
   PARTNER_API_BASE=<테스트 서버 주소>, PARTNER_API_KEY=<테스트 키>
   LOGIN_URL=<테스트 서버 주소>/login
   LOGOUT_URL=<테스트 서버 주소>/logout
   PAYMENT_RETURN_URL=<테스트 서버 주소>/#/golf/payment/return?no={no}
   → API 서버 다시 켜기

2. 로그인 쿠키 옮기기
   테스트 서버에서 가입·로그인
   → F12 → 애플리케이션 → 쿠키 → 테스트 서버 → user_session 값 복사
   → localhost:8787 에서 F12 → 쿠키 → localhost → 이름 user_session, 값 붙여 넣기 → 새로고침

3. 예약 → 결제 (본 사이트가 안내한 테스트 카드)

4. 결제 뒤 테스트 서버 화면으로 가면, 주소를 직접 바꿈
   http://localhost:8787/#/golf/payment/return?no=<GT-로 시작하는 예약번호>
   (주소 앞쪽의 order_id 가 아니라 # 뒤의 GT-... 번호)

5. 끝나면 PAYMENT_BACKEND=fake 로 되돌림
```

- 키가 없으면 로그인 확인부터 모두 실패합니다.
- 로그아웃하면 localhost에 넣은 쿠키는 남지만, 본 사이트에서 세션이 끝나 골프도 로그인 안 된 상태로 바뀝니다.

| 알림 | 할 일 |
|---|---|

| `nights` | 숙박 수 | `2` |
| `base_price` | 1인 기본 가격 (엔) | `180000` |

### 승차 시간 등록하기

```
출발 확정 (출발 7일 전)
 → 출발편별로 예약자의 타는 곳·요청 사항을 보고 순서와 시간을 정함
 → booking_stop 의 PICK 줄에 stop_order (1, 2, 3 …), pickup_time (예: 06:40) 저장
 → 예약자의 예약 상세 화면에 승차 시간 표시 (출발 확정된 예약만)
 → 출발 3일 전까지
```

- **승차 명단**은 같은 데이터로 만들 수 있습니다: 출발편(`departure`) → 확정 예약(`booking`, 상태 `CONFIRMED`) → 예약자·동반자(`booking_member`) + 타는 곳·내리는 곳(`booking_stop`).
- 골프 서버에 등록 API를 두려면 `PUT /api/golf/admin/departures/{id}/stops` 자리를 채우시면 됩니다 (지금은 자리만 있음).

### 예약 취소 알림 (본 사이트 → 골프 서버)

예약 취소·환불을 본 사이트에서 처리한 뒤, 결과를 골프 서버에 보내 주십시오 (4장 A2).

```
POST https://<골프 서버>/api/golf/site/bookings/{골프 예약번호}/cancel
X-Site-Key: <SITE_KEY>
Content-Type: application/json

{ "refundId": "본 사이트 환불 번호 (최대 40자)",
  "refundStatus": "REQUESTED | DONE | FAIL",
  "note": "메모 (선택, 최대 200자)" }
```

| 응답 | 뜻 |
|---|---|
| 200 `{"status": "USER_CANCEL", "refundStatus": "…"}` | 처리됨. 자리 풀림, 예약 취소 메일 발송 |
| 401 | 키가 맞지 않음 |
| 404 | 예약번호 없음 |
| 409 | 예약을 취소할 수 없는 상태 (운행 취소·여행 완료) |

- 환불 상태가 바뀌면 같은 주소로 다시 보내 주십시오. 두 번째부터는 환불 상태만 바뀝니다.
- `FAIL`이면 골프는 다시 환불을 요청하지 않고 운영자 알림만 남깁니다.
- 보안은 지금 나눠 가진 키 하나입니다. 서명이나 IP 제한이 필요하면 `apps/api/app/routes.py`의 `site()`에 더하십시오.
- 운행 취소는 골프 서버가 직접 하므로 보내실 필요가 없습니다.

## 20. 바꾸는 방법 모음

### 최소 출발 인원을 바꾸려면 (예: 15명 → 20명)

1. `apps/api/app/settings.py` `MIN_DEPARTURE`와 `packages/shared/src/settings.ts`의 같은 값을 바꿉니다.
2. 이미 만들어진 모집 중 출발편에도 적용하려면, 새 Alembic 버전으로 `UPDATE departure SET min_people = <값> WHERE status = 'OPEN'`을 넣습니다 (예시: `migrations/versions/0006_min_departure_15.py`).
3. 정원이 20명이므로 20명으로 하면 자리가 다 차야 출발합니다.

### 승하차 범위를 바꾸려면 (반경·중심)

1. `settings.py` `SERVICE_AREA`, `packages/shared/src/settings.ts` `SERVICE_AREA`, `seed/demo_data.json`의 범위를 같게 바꿉니다.
2. 운영 DB에는 새 Alembic 버전으로 `service_area`를 고칩니다 (예시: `0005_service_area_5km.py`).
3. 이미 있는 예약의 장소는 다시 검사하지 않습니다.

### 리조트 패키지만 승하차 범위를 다르게 하려면

지금은 범위가 패키지와 연결되지 않은 공통 목록이라 패키지별로 다르게 줄 수 없습니다. 바꾸려면 다음 순서로 합니다.

1. 패키지 ↔ 범위 연결 표 `package_service_area (package_id, area_id)`를 추가합니다. 연결이 없는 패키지는 지금처럼 공통 범위를 씁니다.
2. 범위 밖이어도 허용할 장소(리조트 호텔·공항 등)는 `package_allowed_place (package_id, name, lat, lng, place_id)`로 둡니다.
3. 서버 `services/booking.py`의 범위 검사(`_area_of`)가 패키지 번호를 받아 그 패키지의 범위·허용 장소만 보게 합니다. 범위 확인 API(`POST /places/check`)에도 패키지 번호를 더합니다.
4. 화면은 패키지 상세 응답으로 그 패키지의 범위를 받아 씁니다 (18장 1번과 같이 하면 편합니다).

### 패키지에 항목을 더하려면 (예: 태그)

1. 새 Alembic 버전으로 `package`에 칸을 추가합니다. 값이 여러 개면(태그·사진 여러 장) `package_tag (package_id, tag)`처럼 표를 따로 둡니다.
2. 서버 응답: `services/catalog.py`의 조회 SQL과 목록·상세 응답에 더합니다. 응답 타입은 `packages/shared/src/api.ts`.
3. 화면과 문구(`i18n.ts` 한국어·일본어)에 더합니다.

### 패키지마다 정원을 다르게 하려면

`package`에 `capacity` 칸을 두고, `services/departures.py` `generate_departures`가 설정값 대신 그 값을 쓰게 합니다. 출발편에는 이미 정원 칸이 있어 판정·남은 자리 계산은 그대로 동작합니다.
